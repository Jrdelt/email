# Threat Model

## Assets & Goals

- **Goal:** Warn users about phishing emails, malicious attachments, and deceptive destination links in webmail while maintaining a low false-positive rate (`<=0.1%` target).
- **Protected assets:** User credentials, session state, local device safety, user trust, and mailbox privacy (zero email bodies, attachment contents/names, sender addresses, or full URLs ever leave the browser).
- **Out of scope (v1):** Deep byte-level attachment sandboxing (inspecting inside encrypted ZIPs, PDFs, or Office binaries), native desktop/mobile mail apps, mobile browsers (Safari, Firefox for Android: never built or tested), and server-side mail gateway filtering.

## Attacker Capabilities

An adversary can send arbitrary HTML emails to the user's inbox and may attempt to:
- Impersonate trusted brands via display names (including compact/camelCase forms, look-alike letters and dots, and a brand's own sender names such as `Apple ID`), look-alike domains (one-letter changes, swapped letters, brand-plus-word combinations like `paypal-secure`, or a brand's domain inside another domain like `paypal.com.evil.example`), punycode (`xn--`), or forged `From` headers sent through third-party relays.
- Disguise malicious links via mismatched anchor text (including text hidden with CSS or reversed with right-to-left overrides inside the link), `@` userinfo authority tricks, multi-hop open/tracking redirects, URL shorteners, sites on free hosting services, raw cloud object storage HTML pages, SVG `href`/`xlink:href` anchors (directly or through `<use>`), or HTML `<form action>` / `[formaction]` submissions.
- Smuggle credential stealers or malware via attachments (`.html`, `.svg`, `.hta`, `.lnk`, `.iso`, `.exe`, `.rdp`, `.iqy`, archives, double extensions like `invoice.pdf.exe`, or inline `data:`/`blob:` downloads, including forms that submit to a `data:`/`blob:` URL).
- Pad or salt the body with hidden text to dilute or split the words the scorer looks for.
- Clobber DOM properties (`<form><input name="getAttribute"><input name="tagName"><input name="closest"></form>`) to crash the scanner or slip past the locks, spoof webmail header CSS classes (or a whole sender chip) inside the message body, or override page styles to hide/restyle security UI.

## Defense Layers & Residual Limits

### 1. Link & Form Locking
Flagged emails pause links (`a`, `area`, SVG `href` & `xlink:href`), `<a ping>` beacons, embedded image links, `<form>` submissions, and `[formaction]` controls by stashing attributes (`data-ped-*`) via prototype-bound helpers (`src/dom.ts`: attributes, `closest`, `contains`, `localName`, `textContent`, `nodeType`, `ownerDocument`, immune to `<form>` DOM clobbering; adapters also skip `<form>` elements as header/attachment candidates, see `isUnsafeNode` in `src/adapters/extract.ts`) and intercepting `click`, `auxclick`, `dragstart`, `submit`, and `keydown` (`Enter`/`Space`) in capture phase (`src/ui/linkLock.ts`), with instant `MutationObserver` re-locking of dynamically inserted nodes.
- *SVG `<use>`:* a `<use>` that shows a link counts as a link. Links behind `<use>` are followed up to 20 links or `<use>` elements and 4 nested levels (`src/dom.ts`); a `<use>` with links beyond that bound is treated as a link in a locked email, and a click on it is always paused, on unlocked emails too.
- *Residual limit:* Users manually copying and pasting plain-text URLs into the address bar.

### 2. Attachment Locking for Untrusted Mail
Native webmail attachment shelves/cards (Gmail, Outlook Web, iCloud Mail, Yahoo Mail, Proton Mail; read only outside the message body) and inline downloads in **any untrusted email**, meaning `a[download]` / `data:` / `blob:` links and a `<form action>` or submit control's `formaction` that submits to a `data:`/`blob:` URL (Chromium saves a non-renderable `data:` response as a file), are locked (`data-ped-att-locked`, stashing `href`, `download`, `download_url`, `formaction`, `action`), even when body text scores safe or after dismissing the banner. The lock refuses `click`, `auxclick`, `dblclick`, `contextmenu`, `mousedown`, `mouseup`, `pointerdown`, `pointerup`, `dragstart`, `submit`, and `keydown`/`keyup` `Enter`/`Space` (`src/ui/attachmentLock.ts`); `touchstart`/`touchend` are kept away from page handlers by a passive listener that does not cancel them, so scrolling still works. A refused click or right-click shows the "Attachment blocked" notice, whose file name comes only from the lock's own isolated-world record, never from page-visible attributes. An attachment control the adapter recognises with no file item in it (a lone "Download all") counts as a nameless attachment and is locked too. Gmail file links are matched on the exact `view=att` parameter.

Local filename inspection (`src/attachments.ts`) highlights dangerous smuggling/executable/double-extension patterns (including `.rdp`, `.ppsm`, `.sldm`, `.xla`, `.searchConnector-ms`, `.iqy`, `.slk`, `.diagcab`, `.msp`, `.msu`, `.scf`, `.ps1xml`, `.msh`, `.appref-ms`, `.dll`) and archives without downloading bytes. Every attachment name, up to 500 per email, is classified; the banner shows at most 50.
- *Inbox list (Gmail):* file buttons on list rows open a file whose email was never opened or scanned, so a click (or Enter/Space, middle-click, drag) on them is refused for every sender with a note to open the email first (`listAttachmentAt` in `adapters/gmail.ts`; click-time only, no idle cost). Every activation path is refused on those buttons, the context menu included. Its selectors are not yet checked against saved real Gmail pages (ROADMAP T7), and list-view file buttons on Outlook, Yahoo and Proton are not guarded yet.
- *Residual limit:* Once the user trusts the email (or its sender), its files open normally, and a malicious payload inside a benignly named file (`.pdf`) is not inspected: file contents are never read.

### 3. Click-Time Destination Inspector & Race-to-Click Gate
**Race-to-click gate.** Clicking a link or submitting a form before the 400 ms debounced scan finishes holds the action and flushes the scan immediately (`isPending` gate). A held action re-checks the message's lock after every wait and right before it proceeds, and is dropped with the "paused" notice if the email became locked meanwhile. While a scan is pending, the click guard extracts the page at most once per DOM change, and Space/Enter typed into text fields is not inspected.

**Destination check (unlocked emails).** A left or middle click on an external `http(s)` link, and a form submission (its destination is the submit button's `formaction`, else the form's `action`, else the page), get the same check (`installClickGuard` in `entrypoints/content.ts`):
1. Redirect and link-protection wrappers are unwrapped locally, up to 4 hops (`src/linkGuard.ts`): Microsoft Defender Safe Links, Proofpoint URL Defense v2/v3, Barracuda, Cisco Secure Email, Google `/url` on Google's own country domains (an explicit list; an empty `q=` or one holding search words falls through to `url=`), the Google AMP viewer `/amp/s/`, Bing `/ck/a` (`u=a1<base64url>`), Facebook `l.php` and YouTube `/redirect`. A wrapper that names more than one destination (conflicting `q=`/`url=`, or a Bing target that cannot be decoded) is "ambiguous" and goes to the warning page.
2. Local URL risk signals. **Danger:** `@` authority disguise, IPv4/IPv6 literal, punycode, raw cloud HTML, a direct download of a risky file type (executables, scripts, disk images, macro documents, `.svg`; `.html`/`.htm`/`.com`/`.dll` count as normal pages), and IP-logger/Grabify traps like `urlto.me`. **Warning** (warning page with a way to continue): archive downloads (`.zip`, `.rar`, `.7z`, ...), URL shorteners, sites on free hosting services (`pages.dev`, `workers.dev`, `web.app`, `firebaseapp.com`, `netlify.app`, `vercel.app`, `github.io`, ..., `on.aws`; never looked up, because the service's own domain says nothing about who runs the site), unencrypted `http://`, and ambiguous wrappers.
3. A destination that passes locally and is on a different registrable domain than the sender's gets a domain lookup (RDAP age, DNS `NXDOMAIN`; disabled in Strict Local Mode). The click waits up to 700 ms for it (`CLICK_INTEL_TIMEOUT_MS`), or up to 2.5 s while the sender's own lookup is still running (`SENDER_INTEL_WAIT_MS`); in that case it also waits for the sender's verdict and is dropped with the "paused" notice if that verdict locks the email. When the lookup does not answer in time, the click goes through.

Risky destinations open `warning.html` through a `browser.storage.session` entry under a random UUID. The entry holds the checked destination URL, the reasons and the lookup result, never a sender field. For an enterprise link-protection gateway (Defender Safe Links, Proofpoint URL Defense v2/v3, Barracuda; https only, and only when it unwraps unambiguously to exactly the checked destination; not Cisco Secure Email or tracking redirectors) it also holds the clicked gateway URL, which is never displayed: "Open anyway" goes through it so the organization's time-of-click check, block page and click log still apply. Such a gateway URL can carry the recipient's own address (Safe Links `data=`). The entry is removed on back, on proceed, or when its tab closes; once older than 1 hour it is dropped when the background starts or at the next link warning or tab close (no timer), and it is gone when the browser closes. The page shows the destination's registrable domain in bold (for a site on a free hosting service, the site on it, such as `evil.pages.dev`, and no lookup of the service), with "Full host name: …" under it when they differ, and the percent-encoded URL, and "Open anyway" names that site. For a form, the warning page gets the destination only, never the form fields, speaks of a form whose answers were not sent, and its "Open anyway" only opens (GET) the action URL without the answers, which it says; a cleared submission is submitted again unchanged. A GET form is checked by the URL the browser requests: the action with its query replaced by the form's fields (including the submit button's), so a redirect target in a hidden field is unwrapped. The warning page then gets the action's site and path, or the destination unwrapped from the fields, never the URL with the fields. The method and action are parsed as browsers parse them (`method=" dialog"` is GET; only ASCII whitespace is stripped from an action).

`#fragment` links count as same-page (and are not checked) only when the document has no `<base href>` or they resolve to the document's own URL.

- *Residual limit:* Only `http(s)` destinations are checked. Links with other schemes, such as protocol handlers (`search-ms:`, `ms-msdt:`, `ms-word:`, `msteams:`, `zoommtg:`), are neither scored nor checked at click time in an unflagged email (`data:`/`blob:` downloads are the attachment lock's job). Pausing them is an open owner decision: an allow-list would also pause common legitimate app links, and the warning page only handles `http(s)`. A narrow option under consideration is a click-time pause for handlers with no legitimate use in email (`search-ms`, `search`, `ms-msdt`, `ms-officecmd`, `ms-appinstaller`).
- *Residual limit:* The guard acts on clicks, middle-clicks and form submissions only. The browser's own context menu ("Open link in new tab/window", "Copy link address") and dragging a link onto the tab strip or address bar fire no event it handles, so on an unflagged email those open without the destination check. Flagged emails are unaffected: their paused links have no `href` left.
- *Residual limit:* The domain lookup fails open after its timeout, and sites on other multi-tenant platforms (`sharepoint.com`, `onmicrosoft.com`, `docs.google.com/forms`) resolve to the platform's own long-registered domain (an open owner decision).
- *Residual limit:* Server-side multi-hop redirects that occur *after* navigating to an aged, reputable domain (without opt-in `webNavigation` permissions).

### 4. Content Scoring Inputs & Work Caps
- **Body text:** up to 20,000 characters (head and tail) are scored. When a body is longer, text that CSS hides (`display:none`, `visibility: hidden/collapse`, font size under 1px, `opacity: 0`, `[hidden]`, `content-visibility: hidden`, zero height/width with hidden overflow; judged from computed style, so stylesheets count; `aria-hidden` is ignored) is sampled after the shown text, so hidden padding cannot push the visible lure out of the sample. Bodies that fit the sample are read whole.
  - *Residual limit:* hiding the extension does not detect (same color as the background, off-screen positioning, 1px fonts); at most 20,000 elements' styles are read per body; a read in each direction stops after about 1M raw characters or 62,000 skipped nodes. In bodies short enough to be read whole, CSS-hidden text still counts, so a hidden splitter inside an urgency keyword (`pass<span hidden>_</span>word`) still hides that keyword.
  - Long emails (over 20,000 characters) that contain hidden text now produce a different body than before, so an "I trust this email" given to one earlier must be given again.
- **Link text** is scored as the reader sees it: CSS-hidden text inside a link is dropped, and text under a right-to-left override (`<bdo dir=rtl>`, `unicode-bidi: bidi-override`, U+202E) is reversed. A mismatch shown by either the DOM text or the rendered text counts. Link text with a punycode or look-alike top-level domain (`www.paypal.cоm`) counts as a shown domain. The sender's own domain shown on a known email-service click-tracking link (`sendgrid.net`, `list-manage.com`, `hubspotlinks.com`, `awstrack.me`, ...) is not a mismatch.
  - *Residual limit:* off-screen positioning, `color: transparent`, `clip-path`, `text-indent` and transforms are not modelled, and nested bidi overrides are only approximated.
  - *Work bound (fail closed):* past 2,000 computed-style reads per scan, or a link-text budget of 25 × 20,000 raw characters plus nodes visited (each link's text is read once; past the budget, further link texts are sampled from both ends), the email is treated like one with too many links: suspicious, with its links paused ("too many links"). The scorer reads at most 250,000 characters of normalized link text per email; past that an otherwise safe email gets "This email has too much link text to check it all, so its links are paused".
- **Names and words:** display names are matched after folding look-alike dots and Cyrillic/Greek look-alike letters ("Claims to be X using look-alike letters"); urgency words are counted after folding look-alike letters inside words that also contain plain ASCII letters (a parity feature, mirrored in `features.py`).
- **Multi-message threads:** body extraction merges every body selector and the inline and iframe sources, so a thread rendered with mixed markup keeps all its messages (this can change which messages a thread's trust fingerprint covers).
- *Residual limit:* **Image-only emails** (a single linked image with empty `alt` text) have no text signals and score as safe, so only the click-time domain check applies, and it fails open. Flagging every email that is essentially one external image link would also flag many legitimate marketing emails, so this is an open owner decision (or a future ML feature, which needs the parity process).

### 5. Spoof-Resistant Allowlist
Sender trust (`trustedSenders`) matches exact validated email addresses only (never domains, wildcards, or display names). Whenever webmail exposes an unauthenticated badge or a conflicting non-ESP `via` relay, `canTrustByAllowlist` refuses auto-trust, disables `"Always trust sender"` in the banner, and surfaces a spoofing warning. A Gmail `via` relay that is not a checkable host name (an internationalized top-level domain such as `.рф`, or an underscore) also refuses auto-trust, with "Sent through a relay server that could not be checked".
- *Coverage:* only the Gmail adapter reads the webmail's sender-verification signals today (`WebmailAdapter.authSignals`), and only when Gmail's interface is in English (`<html lang>` is `en` or `en-*`); localized badge text is not read. On Outlook, Yahoo, Proton, iCloud and non-English Gmail a forged copy of an allowlisted address cannot be told apart, so there "Always trust sender" hides the warning banner but keeps that email's attachments locked behind an attachment notice ("I trust this email" opens them); risky attachment types also keep links paused, as for any unverified email. The notice ranks below every other message's warning, so it never hides one.
- *Sender extraction:* the Gmail sender chip is never read from inside a message body. On Outlook, Yahoo and Proton, an address found only by the adapter's loose header fallback (no explicit From node) is marked uncertain, like iCloud's, and is never auto-trusted from the allowlist; neither is a sender found in a conversation-level fallback when that scope holds another message body or more than one sender address. Attachment names and the subject are never read as the sender, and Proton without a From block reads the sender only from attributes and non-recipient elements. Per-email trust still works for uncertain senders.
- *Residual limit:* Webmail views where authentication metadata is hidden until headers are expanded. Where sender verification is not read, a spoofed trusted sender's links and content are not re-checked; the click-time guard still checks the links clicked and forms submitted there, within the limits of section 3. When a conversation-level fallback is used, the banner may name the conversation's first sender. If Outlook renames its From class (`span.OZZZK`), trusted senders there are scored like everyone else (fail closed).

### 6. iCloud Mail Frames
iCloud renders headers in an app frame and each message body in a cross-origin sandbox frame; the background relays between them statelessly (section "Permissions, Messaging & UI Isolation"). Lock decisions for a message frame are tied to its body by a 128-bit SHA-256 signature (first 32 hex characters) that email content cannot forge. A decision without a signature, or sent before the app frame saw the body, can only tighten the frame's locks: it never unlocks it or releases its held clicks. A click in a message frame waits up to 2.5 s for the app frame's decision. Message iframes navigated in place (`srcdoc` or `src` set again) are rescanned when the old document fires `pagehide`, so a new body whose `load` event never fires is still scanned, locked and guarded.
- *Residual limit:* If the app frame recognizes no open message card (for example after iCloud changes its page), the sandbox bodies are not scored and their frames are released; only the click-time check applies. Scoring card-less bodies instead would warn about stale pooled frames that are no longer on screen, so this needs real iCloud page fixtures and an owner decision.

## Third-Party Domain Lookups & HIPAA Strict Local Mode

By default, lookup services learn the **registrable domain** of opened emails' senders and of clicked external link and form destinations, plus what every browser request carries: the user's IP address, the `User-Agent`, and an `Origin: chrome-extension://<extension ID>` header (Edge: its own store ID) that tells them the request comes from this extension. The ID is the same for every install from a store. Firefox uses a `moz-extension://` origin with a random per-install ID; whether Firefox sends it with these requests has not been checked yet. Removing the header would need a new permission (`declarativeNetRequest`). Mitigations:
- **Strict Local Mode & Enterprise Policy (`src/settings.ts`, `public/managed_schema.json`):** Users can toggle **Strict Local Mode** directly in the popup, or HIPAA/enterprise IT administrators can enforce `strictLocalMode: true` via `browser.storage.managed`, disabling all `domainIntel` `fetch()` calls (0 bytes off-device) across content, click-guard, warning, and background scripts.
- Only two services: IANA/registry RDAP (`rdap.org` fallback) and Cloudflare DNS-over-HTTPS (`cloudflare-dns.com`). There is no spam-list (URIBL) lookup: URIBL refuses queries from public resolvers, so it was removed together with the `dns.google` fallback.
- Strict `isValidDomain` validation before constructing any request URL; `https:`-only registry RDAP bootstrap validation (`Object.create(null)` map + hostname verification).
- `credentials: 'omit'` and `referrerPolicy: 'no-referrer'` on every `fetch`.
- Private-use and special-use TLDs (`.local`, `.lan`, `.corp`, `.mail`, `.internal`, `.home`, ...) are never looked up (`isLookupDomain`), so intranet host names are not disclosed. Sites on free hosting services are not looked up either (section 3).
- *Residual limit:* DNS-over-HTTPS queries for a sender's domain reach that domain's authoritative name servers, so a sender who runs its own DNS can infer that (and roughly when) the email was opened, even when remote content is blocked. The user's IP is not exposed (the resolver asks on its behalf). Strict Local Mode removes the signal.
- 24-hour local cache (`domainIntelCache`, 15 minutes for partial results, newest 200 domains); expired entries are deleted when the background starts and at the next lookup; DNS `NOERROR`/`NXDOMAIN` RCODE verification (ignoring transient `SERVFAIL` errors). Stored answers are bounded (10 MX hosts, SPF and DMARC 1,024 characters, registrar 200 characters, 20 status flags), so a sender's oversized DNS answers cannot fill storage, and a failed cache write never discards a lookup.
- Hardened local report redaction (`feedback.ts` strips attachment names, emails, full URLs, IP literals, and domain names to `[file]`/`[address]`/`[url]`/`[ip]`/`[domain]`) and no sender field inside `warn:*` session warnings (minimum-necessary principle; see section 3 for what the URLs there can contain). The "Copy details for IT" text is not redacted: it is meant for an internal ticket and contains the sender's name and address, domains and attachment names.

## Permissions, Messaging & UI Isolation

- **Minimal install permissions:** Only `storage` and the explicit active webmail match patterns in `extension/src/hosts.ts` (Gmail, Outlook Web including `outlook.cloud.microsoft`, Yahoo Mail, Proton Mail, and scoped iCloud Mail frames `www.icloud.com/mail/*`, `www.icloud.com/applications/mail2/*`, and `*.icloud-sandbox.com/applications/mail2-message/*`). No `<all_urls>`, no `tabs` host access, zero `web_accessible_resources`, and zero runtime npm dependencies.
- **Native attachment blocking on all 5 supported providers:** Works across Gmail shelves, Outlook Aria attachment wells/cards, iCloud mail2 attachment bars, Yahoo attachment tiles, Proton attachment lists, and inline download/data/blob anchors, in opened emails.
- **Sender-verified messaging:** `background.ts` verifies `sender.id` and `isSupportedWebmailUrl(sender.url)` (plus top-frame / iCloud `app`-frame checks on `verdict` and `sandbox`-frame checks on `icloudBody`). The only `window.postMessage` is the iCloud pairing nonce: the app frame posts a random UUID to its card's message iframe, the sandbox reports it back through the background (which adds the verified `sender.frameId`), and the nonce carries no email data and is never trusted on its own.
- **Closed Shadow DOM & strict CSP:** `#ped-banner-host` and `#ped-toast-host` use `attachShadow({ mode: 'closed' })` with `:host { all: initial !important }` mounted on `document.documentElement`, constructed strictly via `textContent` / `createElementNS`. Each script tracks the hosts it made per document instead of looking them up by id, so an email carrying `id="ped-banner-host"` cannot make it delete page content or stack banners. The banner card scrolls when taller than the window, is announced as `role=alert` only when its level or title is new (re-renders use a `region` labelled by the title), and names its finding in its sticker (PHISHING ALERT, ATTACHMENT ALERT, SENDER CHECK, ATTACHMENT CHECK, CHECK LIMIT). Paused-link and attachment notices take host and file names only from the locks' isolated-world records, are not removed by re-renders, and close when a lock that was in place is lifted. Sender name, address and domain text in the details and IT rows is bidi-neutralized. Extension pages enforce `script-src 'self'; object-src 'none'; base-uri 'none';`.
- **Background wake-ups:** the background keeps no timers. Firefox registers `tabs.onUpdated` for status changes only; Chrome and Edge do not support filters on that event, so they wake the background on every tab update, and the listener returns at once unless the status is `loading`.

## Known Limits Awaiting an Owner Decision

- Protocol-handler links (`search-ms:`, `ms-msdt:`, `ms-word:`, ...) are not scored or checked at click time (section 3).
- Image-only emails have no content signals (section 4).
- iCloud message bodies without a recognized message card are not scored (section 6).
- Lookup requests carry the extension's `Origin` header and the browser's `User-Agent` (section "Third-Party Domain Lookups").
